# Automation atomicity and workflow recovery

Repair scope (28 October 2026): prevent concurrent duplicate automation effects and recover workflow finalization after an audit failure. Preserve existing organization grants, HTTP response shapes, MySQL 8.0.44 and Prisma 6.19.3. No schema or migration change.

Automation serializes dispatches using a tenant-scoped `SELECT ... FOR UPDATE` on the existing automation rule row. It reloads the active rule and checks the existing organization/rule/entity/UTC-day idempotency key under that lock. This works across processes without adding a uniqueness constraint or deleting historical execution records. Different rules remain independent. Every engine writer must use this lock protocol; direct database inserts are outside the application guarantee.

Task creation, notification creation, workflow creation/advancement, execution status, last-run time and their audits share one database transaction. Workflow/notification services accept the caller's transaction; they must not start nested transactions or swallow database errors when participating in automation. These actions perform database writes only. Failure rolls back the whole action batch, then records a sanitized FAILED execution and failure audit together under the same rule lock, unless a competing dispatch has already recorded that key. Failure-audit persistence failure propagates instead of claiming a persisted result. Deadlock conflicts have bounded retries. Existing FAILED executions still suppress that day's key; there is no new automatic retry policy or additional privilege grant.

The existing automation:manage authorization remains unchanged: automation CREATE_TASK retains the existing rule-driven task semantics. Workflow business actions still use their current workflow and task/document authorization. No role-name bypass or new grant is introduced.

Workflow retry continues to accept FAILED instances. It additionally accepts RUNNING instances only when every persisted step is already COMPLETED, for recovery of a failed completion transaction. Under the instance lock it rechecks workflow:update/read (or existing workflow:manage), tenant and current persisted state, and records workflow.retried. Recovery only commits instance completion and its audit; it never repeats completed business effects. WAITING, CANCELLED, COMPLETED, and RUNNING instances with unfinished steps remain ineligible. Concurrent completion produces one completion audit; cancellation cannot be reversed. Recovery is explicit through the existing retry endpoint; it does not require a new scheduler or migration.

Regression validation uses disposable MySQL databases with fault injection and concurrent dispatch, including notification/workflow rollback, failure-audit failure, tenant authorization, cancellation and completion recovery. No synthetic attendance or canonical business data is created by these tests.
